How it works

Follow one real question through the system

Seven steps, from indexing to the finished answer. Every candidate, rank, score, quote and timing on this stage was recorded from the running service for one question. Press play, or jump to any step.

Documents

    511,962 documents

    Passages

    3,064,558 passages

    Stored three ways

    Dense vectors768 numbers per passage, a map of its meaning
    BM25 indexword statistics, for exact terms and identifiers
    PostgreSQLthe text around each passage, for the model

    Step 1 of 7 · once, before any question

    Cut the documents into passages and index them twice

    Half a million documents are split into 3,064,558 passages. Each passage is stored as a vector that captures its meaning and as word statistics for exact matching. The surrounding text waits in PostgreSQL.

    • 2.16 hof free GPU time computed every embedding, once
    • 768numbers describe each passage in the dense index

    Ask

    Exact words

    Identifiers and settings such as dp-132-usw and priority=high must match literally. This is BM25's job.

    Meaning

    “Reserved” and “interactive burst credits” can be worded differently in the documents. A dense model finds those.

    Step 2 of 7

    A question arrives in plain language

    Some questions name an identifier, some only describe a symptom. This one is both: it names a pool and a setting, and asks for a value. Exact words matter as much as meaning, so the system looks for both.

    • Realquestion from the benchmark, answered by the live service

    Step 3 of 7

    Search by meaning and by exact words, then fuse

    A dense model ranks passages by meaning. BM25 ranks them by the words they contain. Reciprocal rank fusion merges the two lists. Look at the Jira ticket: BM25 puts it second, and the dense search never lists it.

    • __R_DENSE__ / __R_BM25__document recall in the first 5 passages, dense / BM25 alone
    • __R_HYBRID__after fusion, over 470 benchmark questions

    Step 4 of 7

    Read the question and each passage together

    The 30 best candidates go to a cross-encoder, which reads the question and a passage at once and scores how well they fit. It re-sorts the pool: the ticket BM25 found climbs from 11th to 2nd, and the top five go on.

    • __R_HYBRID__ → __R_RERANK__document recall at 5 passages, fused → reranked (the benchmark's larger reranker)

    Step 5 of 7

    Write the answer, citing each passage

    Claude Haiku 5.5 receives the five passages with the text around them and writes plain prose. Every sentence carries the number of the passage it rests on.

    • 5passages reach the model, from 2 different documents

    Step 6 of 7

    Check every statement against its source

    Does the cited passage exist? Do its numbers and names appear there? Can a judge quote the sentence that supports the statement, and is that quote found word for word? A statement that fails is flagged, never hidden.

    • __PLANTED_CITATION__% / __PLANTED_NUMBER__%of planted errors caught: a moved citation / a changed number

    Step 7 of 7

    Say what is missing, and what it cost

    The response carries a status, the list of what the documents do not say, the result of every check, and the time of every stage. The status is worth reading: answers that admit a gap were right __MISSING_RIGHT__% of the time, the others __REST_RIGHT__%.

    • answered · partial · not foundthe three statuses of an answer

    Plays on its own while you can see it. Arrow keys move between steps.

    Under the hood

    Built like something you would run

    A FastAPI service in front of Qdrant, PostgreSQL and Redis, with the access control, limits, caching and metrics a deployment needs, all of it started by one Compose file.

    Clients

    Browser or API client/demo, curl, any HTTP client

    FastAPI service

    • API keys and per-client rate limits
    • Hybrid retrieval and reranking
    • Cited answers, statement checks, status
    • Answer cache, metrics and health probes

    Backing services

    Qdrant3,064,558 passages, dense and BM25
    PostgreSQLparent passages and documents
    Redisanswer cache and rate limits
    Anthropic APIwrites the answers and judges the citations

    Built offline, once

    1. Corpus download, SHA-256 checked
    2. Cleaning and chunking
    3. Embeddings on a free Kaggle GPU
    4. Parquet shards loaded into Qdrant

    Hybrid retrieval

    Dense vectors and BM25 searched in parallel, fused by reciprocal rank, then a cross-encoder rescoring the best 30.

    Verified citations

    Every statement is checked against the passage it cites. On planted errors the check flags __PLANTED_CITATION__% of moved citations and __PLANTED_NUMBER__% of changed numbers.

    Honest answers

    Each answer is answered, partial or not found, and lists what the documents do not say.

    Access control

    Named API keys compared in constant time, and per-client rate limits kept in Redis.

    Honest failures

    A slow or unreachable backend returns 503, not a stack trace. A load test found the bug that unit tests could not.

    Cache and metrics

    Repeated questions come from Redis at no cost. Prometheus metrics use bounded labels, so cardinality stays flat.

    Measured, not claimed

    A regression gate in CI recomputes every published number, and a nine-check fairness audit guards each comparison.

    Runs anywhere

    One Compose file on macOS, Windows (WSL 2) and Linux, and a documented way to move the whole index between machines.

    Honest limits

    What this does not claim

    A result is only as useful as the list of things it cannot support. These are the three that matter most.

    Not a leaderboard score

    The same small model, __JUDGE__, writes the answers and judges them, and the public leaderboard uses a different judge. The scores compare the systems inside this project, not against other entries.

    One retrieval pass is not enough

    Answers spread over many documents score __W_SEMANTIC__ (semantic), __W_PROJECT__ (project related) and __W_COMPLETENESS__ (completeness). The next step is a fourth system that retrieves again when the first pass is thin; its plan is written, the code is not.

    Speed needs hardware

    An answer took __LATENCY_RANGE__ seconds on an 8 GB laptop with the index mostly on disk. The one-second retrieval target is missed, and documented as missed. A GPU for the reranker and more memory are the fix.

    Deliberately not built: document upload and a queue worker, tracing and dashboards, TLS termination, RAGAS metrics and a hand-written golden set. The README lists what exists and what does not.
