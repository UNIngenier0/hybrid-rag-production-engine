RAG Primer

What Retrieval-Augmented Generation is, how it works, and the handful of things that decide whether yours works in production.

What & why How it works Building blocks Use cases What breaks Evaluation Build checklist

1What it is and why it exists

RAG gives a language model an open-book exam. Instead of answering from whatever it memorized during training, the system first retrieves the most relevant passages from your own documents, then asks the model to generate an answer using only those passages.

Private knowledge

The model never saw your internal docs. RAG brings them in at question time.

Fewer hallucinations

The answer is anchored to real text instead of the model's memory.

Always current

Update the documents and the answers change. No retraining needed.

Verifiable

Each claim can point to a source passage a human can check.

ApproachGood forLimitation
RAGFacts from changing, private or large document sets, with sourcesQuality depends on retrieval
Fine-tuningTeaching style, format or behaviorPoor at injecting facts; costly to keep up to date; no citations
Long contextOne or a few documents that fit in the promptCost and latency grow with every query; accuracy drops on very long inputs

2How it works

Two phases: an offline phase that prepares the documents, and an online phase that runs on every question.

Offline: indexing (once per document)
  1. DocumentsPDF, DOCX, HTML
  2. Parse & clean
  3. Chunksplit into passages
  4. Embed + keyword indexvectors and BM25
  5. Storevector database + metadata
Online: answering (every question)
  1. Question
  2. Hybrid retrievedense + BM25, ~50 candidates
  3. Rerankkeep best ~5
  4. Promptquestion + numbered passages
  5. LLM generates
  6. Verify citations
  7. Answer + sources
Key idea: the LLM is only the last step. If retrieval does not surface the right passage, no model can write the right answer. Most RAG quality work happens before the LLM.

3The building blocks

BlockWhat it doesWhat to know
ChunkingSplits documents into passages that get indexed and retrievedThe biggest quality lever. Too big dilutes meaning; too small loses context. Respect headings and tables, keep metadata (page, section), and consider small chunks for search with their larger parent for context.
EmbeddingsTurn text into vectors where similar meaning means nearby pointsUse the same model for documents and queries. Language and domain fit matter. Changing the model means re-indexing everything.
Vector databaseFinds the nearest vectors fast (approximate search)Needs metadata filtering (by document, date, permissions). Persistence and operations matter more than benchmarks.
BM25Classic keyword scoringCatches exact terms (IDs, error codes, names, acronyms) that embeddings blur.
Hybrid searchRuns dense and BM25 together and merges the rankingsUse rank-based merging such as Reciprocal Rank Fusion; the two scores are not comparable.
RerankerA cross-encoder reads the query and each candidate together and rescores themMore accurate but slower, so apply it only to a short candidate list: retrieve wide, rerank, keep few.
Prompt & generationGives the LLM the passages and the rulesNumber the passages, instruct the model to use only them, and let it say "I don't know".
CitationsLink each claim to its sourceDo not let the model write the source details. Have it reference passage numbers, then verify and resolve them in code.

4Where it is useful

  • Internal knowledge base Q&A
  • Customer support assistants
  • Legal and compliance search
  • Developer documentation help
  • Research and literature review
  • HR and policy questions
  • Sales and product enablement

The common pattern: a large body of text that changes, that the base model has not seen, and where answers must be traceable to a source.

5What breaks in production

A demo on one clean PDF hides these. Real corpora expose them quickly.

SymptomUsual causeFix
Exact IDs and codes are not foundDense-only retrievalAdd BM25 (hybrid search)
Right passage found but ranked too lowCoarse similarity rankingAdd a cross-encoder reranker
Answers cut off or missing contextNaive fixed-size chunkingStructure-aware chunks, parent-child retrieval
Confident but unsupported answersNo grounding checkCite, verify and abstain when evidence is weak
Quality drops after a "small" changeNo evaluation setGolden dataset plus a regression check in CI
Stale or duplicated contentNon-idempotent ingestionContent hashes and versioned re-indexing
Users see documents they should notPermissions checked after retrievalApply access filters inside the search query
Document text steers the modelPrompt injection through retrieved contentTreat retrieved text as untrusted data, never as instructions

6How to evaluate it

Measure retrieval and generation separately, so you know which one to fix.

Retrieval: did we find it?

Recall@k: is the right passage in the top k?
MRR and nDCG: how high is it ranked?

Generation: did we use it well?

Faithfulness: is the answer supported by the passages?
Answer relevancy: does it address the question?
Context precision / recall: was the retrieved context useful and complete? (RAGAS covers these.)

Build a golden dataset of real questions with the expected source passages and reference answers, and include questions the corpus cannot answer to test abstention. Always debug retrieval first.

7Build checklist

  1. Write the evaluation set firstCollect realistic questions, expected sources and a few unanswerable ones.
  2. Get parsing rightHeaders, footers, tables and scanned pages quietly ruin chunks.
  3. Chunk with structure and metadataKeep section paths and page numbers for filters and citations.
  4. Baseline with hybrid retrievalDense + BM25 + RRF, then measure against dense-only.
  5. Add reranking and measure the gainKeep it only if the metrics and latency justify it.
  6. Ground the prompt and allow abstentionNumbered passages, "use only these", and a confidence threshold.
  7. Verify citations in codeCheck that every marker maps to a retrieved passage and supports the claim.
  8. Make ingestion idempotentHash content, version documents, replace old chunks safely.
  9. Log every stageCandidates, scores, rerank order and verification, so wrong answers can be explained.
  10. Secure itAccess filters at query time, untrusted-context handling, auth and rate limits.
Rule of thumb: change one thing at a time and re-run the evaluation. Every chunk size, model or threshold is a hypothesis until a metric confirms it.
